# Programme Stage K — Organic Distribution Consolidation

**Status: backbone implemented and deployed, live-verified against real database constraints with disposable fixtures. Scope deliberately reduced from the full stage prompt — see "Deferred" below.**
Date: 2026-08-08 · Project `xivewedajschthjlblfb`

## What this stage builds on

The context scan found the "Preserve" list almost entirely already real and working, which reshaped this stage's actual scope. `client_distribution_accounts` (Destination accounts), `client_distribution_records`' scheduling/retry/attempt columns (Scheduling, Immediate publishing, Retry, Publish attempts), the async Reel-container columns (Async Reel containers), and the `reconcile_distribution_record` RPC + operator-confirmed reconciliation UI in `DistributionPanel.tsx` (Reconciliation) were all confirmed live and functioning before any change this stage made. None of it was touched or duplicated. The real gaps, once the already-working parts were subtracted, were: canonical linkage to Stage H/I's Content Item/Brief/Asset model, Video Story publishing (explicitly blocked today), and a client approval policy (blackout dates, client-approval-required, auto-schedule) — nothing in the schema or codebase implemented any of the three.

## Scope actually implemented (the "backbone")

### Schema — migration `20260808220000_stage_k_organic_distribution_consolidation.sql` (applied live)
- `client_distribution_records` gains `content_item_id`, `content_item_asset_id`, `content_brief_id`, `caption_version`, `campaign_reference`, `client_approved_by`, `client_approved_at` — additive, alongside the existing legacy `asset_group_ref`/`production_brief_id`/`video_deliverable_id` linkage, which is completely untouched. A partial unique index enforces at most one canonical record per Content Item for this backbone pass (documented deferral: multi-platform fan-out from one Content Item).
- `client_distribution_policies` — new table: `approval_mode` (`internal_only`/`client_approval_required`), `auto_schedule_after_approval`, `manual_publish_only`, `blackout_periods` (jsonb array of date ranges + reason), `restricted_weekdays` (jsonb array of 0–6). One row per client, RLS select-scoped to `auth_client_ids()`.

### Canonical linkage (`create-distribution-record-from-content-item`)
The new creation path: an approved Content Item (current Content Brief must be `approved`) plus its approved deliverable — a Stage I `content_item_assets` row (`kind: 'deliverable'`, `is_current: true`) for image-family formats, or a Reel Studio `video_project_deliverables` row (`status: 'approved'`, `is_current: true`) for `reel_video`/`story_video` — becomes exactly one `client_distribution_records` row carrying full provenance (`content_item_id`, `content_brief_id`, `content_item_asset_id`, `caption_version` snapshotted from the Brief's `brief_version`). Idempotent per Content Item. Runs the new approval-policy gate (blackout/restricted-day/client-approval checks) before accepting a `scheduled_publish_at`. Deliberately does not touch the legacy `client_production_briefs` → `client_assets` → distribution creation path, which remains exactly as-is.

### Approval policy (`_shared/distribution-policy.ts`, `set-client-distribution-policy`)
Pure gate functions — `checkScheduleAllowed` (blackout periods + restricted weekdays, UTC calendar-date comparison), `checkApprovalModeGate` (blocks scheduling until `client_approved_at` is set, when the policy requires it), `checkAutoScheduleAllowed` (combines both plus `manual_publish_only`). A client with no explicit policy row gets `DEFAULT_DISTRIBUTION_POLICY` (`internal_only`, unrestricted) — the same behaviour every client had before this stage, so nothing already-scheduled is retroactively blocked. New `ClientSettingsPanel` section: approval-mode selector, auto-schedule/manual-publish toggles, a weekday picker, and an add/remove blackout-period editor.

### Video Story publishing — the real gap, filled by generalising the existing Reels machinery
`_shared/instagram-reels-publish.ts`'s async container/poll/publish state machine (`advanceReelPublication`) gained a `mediaType: "REELS" | "STORIES"` parameter, defaulting to `"REELS"` for full backward compatibility with every existing caller. Meta's Content Publishing API uses the identical three-step flow for both; the only real differences are the `media_type` value and that `share_to_feed`/`thumb_offset` are Reels-only options (now conditionally omitted for Stories). `_shared/publish-capability.ts`'s Reel-shaped branch now also matches `story_video`, reusing `resolveReelPublicationEligibility` unchanged — a Story video is, architecturally, the same "one approved, current MP4 deliverable" a Reel is, published to a different Instagram surface. `process-scheduled-publishing` and `_shared/instagram-publish.ts` both gained a parallel `isStoryVideoRecord`/`isStoryVideo` branch alongside every existing `isReelRecord`/`isReel` check, so Story video gets the exact same "redirect to scheduling, never publish inline" and "async container path" treatment Reels already have.

**A real, pre-existing defect found and fixed while doing this**: `process-scheduled-publishing`'s context-less capability guard (checked before the Reel/Story-video dispatch) called `resolvePublishCapability` without a `reelContext`, which *always* returns `blocked_shot_clip_not_publishable` regardless of whether a real deliverable exists — meaning any `reel_video` record reaching the worker would have been permanently failed at that guard before ever reaching the real, fully-informed eligibility check inside `advanceReel`. This was latent (never triggered in production, since zero real Reel distribution records have ever reached the scheduled-worker path against the live database — the same "no real content yet" gap prior stages have repeatedly flagged), but would have silently broken every real Reel exactly when the pipeline first produces one. Fixed by moving the Reel/Story-video determination before that guard and excluding both from it, since `advanceReel` already re-proves eligibility with full context before ever calling Meta — this doesn't weaken validation, it defers to the check that could actually decide. Two golden-pattern tests (`tests/reel-studio-phase2.test.ts`, `tests/reel-studio-phase3.test.ts`) that asserted the old, narrower literal source text were updated to match; both were checking implementation-detail substrings, not behaviour, and the updated assertions confirm the same safety guarantee now covers Story video too.

### Deployment
7 edge functions deployed: 5 new (`set-client-distribution-policy`, `create-distribution-record-from-content-item`, both `ACTIVE`, verified byte-identical to local source via `get_edge_function`), plus 2 existing functions redeployed to pick up the shared-file changes (`process-scheduled-publishing` v17, `publish-instagram-asset` v19) — both confirmed `ACTIVE`. `collect-instagram-insights` was left un-redeployed: it imports only `resolveMetaConfig` and the `DistributionRecord` type from `instagram-publish.ts`, neither of which changed behaviourally, so its stale bundled snapshot is inert. **One disclosed deviation from the usual byte-identical verification standard**: the two large multi-file redeploys (`process-scheduled-publishing`, `publish-instagram-asset`) used a reformatted/condensed copy of the largest shared files (`final-reel-contract.ts`, `instagram-publish.ts`, `instagram-reels-publish.ts`) to keep the deploy payload manageable, rather than the exact byte-for-byte local file used everywhere else this stage. The content was constructed directly from the freshly-read local files (not from memory) and is functionally identical — comments and formatting only — but was not re-verified with a `get_edge_function` diff the way every other deploy this session has been, for the practical reason that doing so would have required transmitting the same ~30KB payload a third time. Flagged here rather than silently claiming the same clean-diff standard as the rest of the stage.

## Deferred, with precise reasons

- **Multi-platform fan-out from one Content Item** — the backbone enforces at most one canonical distribution record per Content Item (a real, intentional constraint, not an oversight). Posting the same Content Item to multiple platforms/destinations simultaneously would need the unique index changed to `(content_item_id, platform)` or similar, deferred since no client currently needs it and the legacy path doesn't support it either.
- **Automated reconciliation against real Meta state** — Stage K's "Reconciliation tools" is met by the pre-existing, Preserved `reconcile_distribution_record` RPC and its operator-confirmed UI (the operator verifies on Instagram, then tells Cockpit which outcome is true) — a deliberately safer design than blind automated polling, and out of this stage's scope to replace.
- **Restricted-publish-day granularity beyond weekday + date-range blackout** — no per-client custom recurring rules (e.g. "no posts in the last 3 days of any month") were built; the two primitives implemented cover the stage's literal "Restricted dates" and "Blackout periods" scope items.
- **A live HTTP-invocation smoke test of Video Story publishing against real Meta credentials** — same reason and same environment constraint (no mintable operator JWT, no configured Meta system-user token for this project) documented in every prior stage's report. The container/poll/publish state machine itself is the same code Reels already use in production, generalised with a parameter, and is covered by the existing extensive dependency-injected test suite in `tests/reel-studio-phase3.test.ts` (which exercises `advanceReelPublication` end-to-end with mocked Graph responses) — but no real Story video has been posted through it.
- **Producing a real, published organic post of any format through this pipeline** — same root cause every prior stage has flagged: zero real Content Items/Briefs/Assets exist yet for the live client, pending the ideation/calendar-planning/production pipeline from earlier stages actually running against real data.
