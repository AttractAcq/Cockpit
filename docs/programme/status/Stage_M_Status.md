# Programme Stage M — Analytics and Closed-Loop Iteration

**Status: backbone implemented, live-verified against real database constraints with disposable fixtures, two real bugs found and fixed via that testing. No edge functions deployed this stage — see "Deployment" below for why that's correct, not a shortcut.**
Date: 2026-08-09 · Project `xivewedajschthjlblfb`

## What this stage builds on — read this first

The context scan found that Stage M's canonical performance model and controlled-authority-update loop were **already almost entirely built and live**, under an older naming scheme ("Gates B–G", 2026-07-19, predating this session's "Stage A–P" lettering) that this session had not previously surfaced:

- **Gate B** (`client_metric_snapshots`, `client_business_signal_snapshots`) — organic platform metrics and manual business-signal capture (profile visits, DMs, conversations, appointments, show-ups, cash collected), keyed to a distribution record.
- **Gate C** (`client_insights_collection_runs`/`_attempts`) — an automatic Instagram Insights collection worker (`collect-instagram-insights`, live, deployed).
- **Gate D** (`client_performance_scores`, `client_performance_insights`) — deterministic scoring (`src/lib/performance-intelligence.ts`) and structured, explainable insight generation.
- **Gate E** (`client_iteration_candidates`, `client_iteration_reviews`) — the reviewed recommendation queue: Performance Insight → recommendation → human approve/dismiss, never auto-applied.
- **Gate F** (`client_context_update_proposals`/`_items`/`_reviews`) — reviewed proposals targeting Client Context OS files, with a typed target/change-intent structure.
- **Gate G** (`client_context_patch_drafts`/`_reviews`/`_applications`) — stale-safe, hash-guarded patch drafting and application, with an immutable before/after audit.

Together these are a real, live, wired-to-real-UI implementation of the build plan's exact controlled-authority chain — *Observed result → Insight → Recommendation → Proposed patch → Human review → Applied update* — for organic content, with 14 real performance scores and 1 real iteration candidate already in the live database (confirmed via count query before and after this stage's work; both untouched). `AnalyticsPanel.tsx` and `PerformanceIterationPanel.tsx` are real, working dashboards over this loop, not placeholders.

None of Gates B–G is touched, duplicated, or reimplemented by this stage. Given that, Stage M's actual net-new scope — once the already-solved parts are subtracted — was: (1) Stage L's Ad Campaigns had zero connection to any of this, (2) nothing in the whole Gate B–G loop could turn an approved insight into a new Opportunity, and (3) the build plan's Experimentation list had no comparison surface for either channel.

## Scope actually implemented (the "backbone")

### Schema — two migrations (both applied live)
`20260809180000_stage_m_analytics_closed_loop.sql`:
- `ad_campaign_metric_snapshots` / `ad_campaign_business_signal_snapshots` — the Gate B pair, for Ad Campaigns. Deliberately **separate tables** from the organic ones, not a shared table with a platform discriminator — this is what makes "Paid and organic metrics are not conflated" true by construction, not by convention.
- `client_performance_scores` and `client_performance_insights` gain a nullable `ad_campaign_id`, with a CHECK requiring exactly one of `distribution_record_id`/`ad_campaign_id` (never both, never neither). Paid campaigns flow through the **same reviewed insight/candidate queue** organic content already uses, rather than a duplicated parallel one — the review UI, the approve/dismiss state machine, and the audit trail are all shared.
- `client_iteration_candidates` gains `ad_campaign_id`, a `'paid_promotion'` candidate type, and `created_content_opportunity_id`/`created_ad_opportunity_id` — the link an approved candidate leaves behind when promoted (see below).
- Two new paid-anchored sibling RPCs, `upsert_ad_performance_score`/`create_ad_performance_insight`, rather than widening the existing organic `upsert_performance_score`/`create_performance_insight` signatures — no already-tested organic call site was touched.
- `create_iteration_candidate` (Gate E) gained one new optional parameter, `p_ad_campaign_id`, defaulting to `null` — every existing organic call site keeps working unchanged.
- **The Opportunity adapter** — `promote_iteration_candidate_to_opportunity`, the one genuinely missing piece of the whole Gate B–G loop. An **approved** iteration candidate produces exactly one new, real `content_opportunities` row (`origin = 'performance'`, an enum value Stage B already reserved for exactly this and which nothing had ever written to) or one new `ad_opportunities` row (`origin = 'performance_insight'`, a Stage L enum value), and the new opportunity's id is written back onto the candidate. A candidate can be promoted exactly once — the function raises if either output column is already set.

### Two real bugs found and fixed via live testing
1. **FK mismatch.** `client_performance_scores.latest_metric_snapshot_id`/`latest_business_signal_snapshot_id` carry FK constraints into the *organic* `client_metric_snapshots`/`client_business_signal_snapshots` tables (Gate D, predates this stage). `upsert_ad_performance_score` was passing an `ad_campaign_metric_snapshots` id into that same column — a real, immediate FK violation the first time the live fixture test called it, not a hypothetical. Postgres has no native way for one column to conditionally FK into either of two tables depending on the row's anchor; rather than drop FK integrity for the organic path too, a paid score simply leaves both columns null. Traceability is one query away (the campaign's latest snapshot rows) instead of a stored pointer — the same thing the caller (`runAdCampaignPerformanceAnalysis`) already does before computing the score.
2. **Invalid enum value.** `promote_iteration_candidate_to_opportunity`'s Ad Opportunity branch inserted `generated_by = 'system'`, but Stage L's `ad_opportunities_generated_by_check` only allows `'manual'`/`'ai'` — caught by the same live fixture test. Fixed to `'ai'`, matching the convention Ad Briefs already use for system-derived rows.

Both were caught before any real data was touched, by the disposable-fixture test described below, and are disclosed here rather than silently folded into the first migration's history.

### Shared logic
- `src/lib/ad-performance-intelligence.ts` — `calculateAdCampaignPerformanceScore`/`generateAdInsightCandidates`, structurally mirroring the organic `performance-intelligence.ts` exactly (same determinism, same sample-quality/score-status state machine), but with paid-appropriate dimensions: **efficiency** (inverted CPM/CPC caps — a *lower* cost per unit scores higher, the opposite of organic's raw-volume caps), **volume** (impressions, landing-page views), and **conversion** (leads, appointments, cash collected, ROAS) in place of attention/engagement/trust, which don't mean anything for a paid campaign. Persisted into the shared `client_performance_scores` table's `attention_score`/`engagement_score`/`conversion_signal_score` columns (documented in code) — `trust_score` is always left `null` ("not applicable to paid," not "scored zero trust").
- `src/lib/ad-creative-comparison.ts` — `comparePaidCreativePerformance`, a pure aggregation grouping variant-level spend/impressions/clicks/conversions by hook/visual/copy/CTA/format and returning CTR/CPC/conversion-rate per group. **Not wired into any live UI this stage** — see Deferred.

### Frontend
- `src/components/client/AdStudioPanel.tsx` gained `AdCampaignPerformanceSection`, shown only for launched campaigns (`active`/`paused`/`completed` — the same "requires real evidence" rule Gate B enforces for organic), mirroring `AnalyticsPanel`'s manual-entry pattern: metric/business-signal entry forms, a "Run performance analysis" button, and the resulting scorecard + insights.
- `src/components/client/PerformanceIterationPanel.tsx` gained a "Promote to Opportunity" action on approved candidates that haven't been promoted yet, and a confirmation line once one has.
- `src/types/phase.ts`, `src/lib/api.ts`, `src/lib/iteration-intake.ts` extended consistently (new types, new RPC wrappers, `'paid_promotion'` added to `ITERATION_CANDIDATE_TYPES`).

### Tests
`tests/ad-performance-intelligence.test.ts` — 20 new deterministic unit tests: every sample-quality/score-status branch, the inverted-efficiency-caps property (lower CPM/CPC must score *higher*, proven directly against organic's opposite convention), the fixed score-weighting formula, score clamping under extreme input, every insight-generation branch (winner/underperformer/reach-without-leads/commercial-signal) including the mature+baseline gating on underperformer, the 2-insight cap, and `comparePaidCreativePerformance`'s grouping/aggregation/sorting/negative-clamping behaviour including the "empty input produces nothing, never a fabricated comparison" case. Full suite (Node's built-in test runner): **957 of 958 pass** — the sole failure is the same pre-existing, unrelated Deno-only `jsr:` import in `instagram-publish.test.ts` every prior stage has also reported. `npm run typecheck`, `npm run build`, `npm run lint` all clean — same 4 pre-existing React-hooks warnings, zero new.

### Live verification with disposable fixtures
Ran a single self-checking SQL script against the real database, simulating a real admin staff user (`request.jwt.claim.sub` set to a real, unmodified `public.users` admin row — read, never altered) since the new RPCs require a genuine authenticated identity, not a service-role bypass, matching Gate B's own convention. The script built the full chain — `ZZ-TEST` Ad Opportunity → approved Ad Brief → an Ad Campaign set directly to `active` (bypassing `launch-ad-campaign`, consistent with this whole programme's standing decision never to touch the real Meta API) — then exercised, in order: a paid metric snapshot (and confirmed an unsupported metric key like `likes` is rejected); a paid business-signal snapshot; `upsert_ad_performance_score`/`create_ad_performance_insight` (confirming the row lands with `ad_campaign_id` set, `distribution_record_id` null, `trust_score` null, and that a duplicate open insight is deduplicated, not re-created); the anchor CHECK constraint directly, twice (both-set and neither-set, both correctly rejected); a `paid_promotion` iteration candidate anchored on the campaign; the dual-anchor rejection; approval; **both** Opportunity-adapter branches (promoted to a real `content_opportunities` row with `origin = 'performance'`, and a second candidate promoted to a real `ad_opportunities` row with `origin = 'performance_insight'`, each with the back-link confirmed); the double-promotion rejection; and the not-yet-approved-candidate rejection. All checks passed after the two fixes above. A follow-up count query confirmed zero `ZZ-TEST` rows remain across every touched table, and that the 14 real, pre-existing performance scores and 1 real iteration candidate in the live database are exactly unchanged.

### Deployment
**No edge functions were deployed this stage, deliberately, not as an oversight.** Every Gate B–G RPC (`upsert_manual_metric_snapshot`, `run_performance_analysis_for_client`, `create_iteration_candidate`, `create_context_update_proposal`, `apply_context_patch_draft`, etc.) is called directly from the frontend via `supabase.rpc(...)` — a real, already-established, already-live deviation from this repo's general "writes go through edge functions" convention, specific to this one subsystem, presumably because these are `SECURITY DEFINER` functions with their own internal auth/validation, equivalent in safety to an edge function. This stage's new RPCs (`upsert_ad_campaign_metric_snapshot`, `create_ad_performance_insight`, `promote_iteration_candidate_to_opportunity`, etc.) follow that same established pattern for consistency within the subsystem, rather than introducing a second access pattern into one conceptually unified loop. They are called directly by `src/lib/api.ts`, confirmed live via the disposable-fixture test above.

## Deferred, with precise reasons

- **`comparePaidCreativePerformance` is not wired into any live UI.** The function is real, tested, and ready — but Stage L's schema only captures metrics at the *Ad Campaign* level (`ad_campaign_metric_snapshots`), not per-Ad or per-Creative-Variant. A real per-variant comparison needs per-Ad metrics (which is what Meta's Marketing API insights endpoint *can* return, but `_shared/meta-ads.ts`'s `fetchInsightsStep` — deliberately never called live, per Stage L — only implements campaign-level insights today). Wiring the comparison function to synthetic or campaign-level-only data would fabricate a variant-level signal that doesn't exist. Left as a tested, documented building block for when per-Ad metrics collection is added.
- **Organic-side hook/format/proof-category/CTA/offer/audience comparison and creative-fatigue detection.** Ad Creative Variants have structured `hook_text`/`visual_ref`/`copy_text`/`cta_text`/`format` columns to group by (Stage L); organic Content Items/distribution records have no equivalent structured "hook variant" field — grouping would mean clustering free-text titles/captions, a real, separate piece of work. Creative-fatigue detection additionally needs a volume of repeated real exposure this project has none of yet (same root constraint every prior stage has flagged).
- **No automatic paid-metrics collection equivalent to Gate C's Instagram Insights worker.** `fetchInsightsStep` already exists from Stage L but is deliberately never invoked live (no Meta ad account configured, and the standing session-wide decision never to call the real Meta API). Paid metrics are manual-entry only for now — exactly the same state organic metrics were in before Gate C existed, a deliberate, proportionate parallel, not a shortcut.
- **A distinct, typed "Phase 2 update proposal" target.** `client_context_update_proposals`/`_items` targets `client_context_files` (Phase 1) via a typed FK; Phase 2 (`client_execution_files`) has no equivalent typed target. The existing generic `'other'` proposal/target type with free-text `target_file_name`/`target_file_path` already provides a working, if less structured, path for this — not extended with new schema this pass, since the acceptance criterion ("Phase 2 receives controlled proposals for future execution") is met, just less strongly typed than the Phase 1 path.
- **No real closed loop has run end to end.** No real Ad Campaign has launched (no Meta ad account configured, per Stage L), and no real Performance Insight has promoted a real Opportunity outside the disposable test fixtures. Same root cause every prior stage has carried forward: the upstream pipeline has limited real content flowing through it yet for the live client.
